# Deployment and recovery runbook

These are operator procedures, not claims that deployment, backups or recovery have run. The local audit on 15 October 2026 found a development environment, a current `c4d9e6f135ab` schema, and a runtime DB role without superuser, role/database creation, RLS bypass, database ownership or ownership of public tables. Production data was queried read-only. No production migration, grant, backup, service installation or reprocessing was performed.

## Install and acceptance

1. Prepare a dedicated host and user. Review `nginx.conf` and `inboxnizer.service`; replace example domains/paths. Only `frontend/dist` belongs in the static root. Store the environment file and Google client outside that root; restrict their permissions. Use a separate schema-owner connection for migrations. The runtime account must not own the database/schema/tables or have DDL privileges.
2. Set the production environment and both exact HTTPS Google callbacks from `README.md`. Preinstall the selected local model files and embedding cache for the service account. The service is offline for model downloads. Inspect Linux filesystem access and the memory cap against real resident memory before enabling it; this Windows workspace cannot validate systemd or nginx.
3. Build and test the frontend/backend. Run `nginx -t` and `systemd-analyze verify deploy/inboxnizer.service` on the target host, then install the reviewed service. Enable restart-on-failure. Boot/restart and inspect only sanitized status/type messages. Never enable SQL parameter logging, traceback/APM local-variable collection, request body capture, Cookie/Authorization headers or query-string logging.
4. Probe `/api/health/live` for process liveness and `/api/health/ready` for config, schema and runtime-role readiness. Both disclose only bounded status. Readiness performs read-only metadata SQL and no model load, mailbox read, Gmail request or inference. It is not proof that models, Google consent or all product paths work. A readiness failure removes the instance from traffic; avoid restart loops for an unavailable DB. The DB pool waits at most 5 seconds; connect timeout is 5 seconds; SQL statements are capped at 30 seconds and lock waits at 5 seconds. Give the external readiness checker a 40-second budget and alert after sustained failure, not on a single miss.
5. Confirm TLS, Secure/HttpOnly/host-only cookies, Google login, session restore/logout, both Google callbacks, direct SPA deep links, CSP, blocked cross-origin mutation, tenant separation and no secrets in static assets on the deployed origin. Capture status and timings only. Keep public traffic disabled until the independent quality and Google-review gates pass.

## Capacity and monitoring

The example uses one worker: additional workers duplicate the classifier, embedding model and local LLM in RAM. It admits only four simultaneous connections at Uvicorn (including connection overhead), returns overload responses, and rate-limits login/consent and Ask at nginx. These are conservative limits for an unmeasured small host, not a measured concurrency guarantee. The ten-connection DB pool allows for separate authentication and owned request sessions; reducing it below twice admitted DB work can create pool contention. Adjust admission and pool limits together only after a mixed workload test. The 3/4 GiB memory thresholds and two-CPU quota are examples to review, not a promise that all model combinations fit. The audit workstation had roughly 1.5 GiB free RAM; loading a large reranker alongside the other models is not justified by that snapshot.

Monitor latency by route class/status, aggregate error counts, readiness, worker RSS, swap, CPU, disk capacity, DB pool waits, sync duration and bounded provider failures. Do not attach questions, email IDs, subject/sender/body, tokens or provider response strings to metrics. Exercise one local LLM generation alongside Inbox/Search, one bounded Gmail sync, and session restore before increasing traffic. Database and inference saturation must produce a recoverable busy state. Rate limiting depends on nginx; the backend must remain loopback-only. Client IP forwarding assumes this nginx is the sole trusted proxy.

Sync now persists continuation and limits each request to five message IDs, two listing pages of at most 50 records, five reconciliation deletions and one prior enrichment retry. A 20-second soft budget is checked between operations; one provider/model operation may exceed it. Source, stage and checkpoint transactions commit separately, and long classifier/summary/embedding computation runs outside database transactions. A dedicated connection holds a per-account session advisory lock until the batch finishes. Settings offers explicit Continue sync; it is not an unattended scheduler. See BOUNDED_SYNC.md for migration, recovery and operational limits. Target-host provider/model latency and mixed-workload capacity still need measurement; the four-connection setting is not a capacity guarantee.

The opt-in `test_runtime_performance.py` benchmark uses only the guarded `_test` database and rolled-back synthetic data. Set `INBOX_BENCHMARK_OUTPUT=results/release-readiness-20261015/runtime-performance.json`, then run `python -m pytest test_runtime_performance.py -q`. It measures sequential Google-session server work with a mocked provider, session restore, Inbox/Tasks and no-change incremental sync with mocked history. Its sample counts, warmups, nearest-rank p95 and exclusions are written into the output. It provides no Google network, model inference, production DB-pool, TLS/proxy or concurrent-load measurement.

## Backup and restore

- Before migration or activation, pause sync/reprocessing and record schema revision, selected model/extractor manifests, aggregate row counts and checksums. Use a dedicated backup role and a custom-format `pg_dump` from a matching PostgreSQL client. Supply credentials through a protected service/password file; do not place passwords in command arguments or shell history. Write backups outside the repository/web root with restrictive permissions and encrypt them at rest.
- Keep an encrypted off-host copy, with separate protected copies of every required `OAUTH_TOKEN_KEYS` generation and model/config manifests. Database backups contain private mailbox data; `.gitignore` is an accident guard, not encryption. Existing local backups are preserved and ignored. Decide and record retention, deletion propagation, RPO and RTO with the operator; no unverified schedule is asserted here.
- Prove a restore into a distinct disposable database before relying on a backup: inspect `pg_restore --list`, restore schema/data, verify aggregate counts/checksums, migration head, FK integrity and credential decryption without printing plaintext. Then run isolation and read-only product smoke against the restored environment. A backup file's existence is not restore evidence.
- Rehearse database and key loss independently. A backup without its encryption keys cannot recover Gmail refresh credentials. Removing an old key requires re-encrypting retained credentials and addressing backups protected by that key.

## Migration, activation and rollback

Only after release gates pass: take/verify backup; stop writes; run reviewed Alembic upgrades using the separate owner connection; reapply reviewed least-privilege grants where needed; check head/counts; deploy the chosen model/extractor manifests; restart the runtime service; verify readiness and smoke. Do not let the runtime service run automatic migrations. The previously audited local DB is at c4d9e6f135ab; this pass adds d5ea7f246bc0 for sync continuation. It has NOT been applied to production. Apply it only through the separate migration owner before deploying the new sync code; readiness rejects the old schema. Do not repeat historical setup blindly.

Bulk reprocessing is a separate gated operation: bound batches, retain source email data, record before/after version counts, use idempotency, and stop on integrity/quality regressions. It is intentionally not executed by this pass. Keep the previous code/model artifacts and DB backup together. Rollback first restores the previous application artifacts if schema compatible; for incompatible changes, isolate traffic and restore the verified backup into a separate replacement database, validate, then switch configuration. Do not run destructive downgrades against live mailbox data as a shortcut.
