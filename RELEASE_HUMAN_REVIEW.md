# inbox-nizer human review before release

No labels or judgements were generated by the agent. Keep all mailbox exports local; do not commit, upload or email them. `private_review/` is ignored by Git. Review one development file at a time; leave every holdout separate and unopened during selection/tuning.

## Classification

For a simple one-email-at-a-time screen with autosave, run `.\env\Scripts\python.exe -m quality.local_classifier_review` and open the private localhost URL it prints. It prioritizes 50 development emails. See [local screen instructions](LOCAL_CLASSIFIER_REVIEW.md).

Default local export (not supplied in Git): `private_review/development.csv`.

Review counts depend on your local export. Keep any adjacent `holdout.csv` unopened during development. An export sampled by predicted-category/confidence strata is a diagnostic review queue, not by itself a representative release sample.

Review subject, sender, date and original body. Fill `gold_label`, `ambiguous=yes/no`, and `reviewer`. Valid labels: Business; Customer Support; Events & Invitations; Finance & Bills; Job Application; Newsletters; Personal; Promotions; Reminders; Travel & Bookings. Do not force ambiguous mail into a category. Business includes professional networking; Finance requires an actual financial obligation/transaction rather than a profession mentioning banking. A specific hiring/application process belongs under Job Application.

For the final evidence tooling, add columns `label_source` and `reviewed_at`. Only the actual human reviewer should enter `human_reviewed` and the review date (`YYYY-MM-DD`) after reviewing a row. Do not mark weak/generated labels as human. Keep original exports and IDs intact. Once development labels exist, compare existing candidates only. Freeze the selected artifact/policy and review manifest before one final holdout evaluation with `quality.classifier_release`. Do not repeatedly test holdout or report this stratified queue as representative accuracy.

## Tasks and deadlines

Open `private_review/final-gate-20261017/tasks/tasks-development.csv` (local export). Keep the task holdout separate. Columns contain original mail and this extractor's numbered predictions; no existing model prediction is treated as truth.

Fill `gold_task_count` with the number of actual user actions, including missed actions. Fill `correct_task_indices` as a JSON array of the correct prediction numbers, starting at 1 (for example `[1,3]`; use `[]` for none). Count an action once, even if predicted twice. Fill `gold_deadline_count` with actual action-linked deadlines, including missed ones. `correct_deadline_indices` lists predictions whose date and association are both correct. Event/sent/invoice dates do not count unless they govern the action. Mark `ambiguous=yes/no`, reviewer, human provenance and review date. Ambiguous rows are reported separately.

Run development scoring:

    .\env\Scripts\python.exe -m quality.release_review score --kind tasks --csv private_review/final-gate-20261017/tasks/tasks-development.csv

Empty review cells produce pending counts and unavailable metrics, never fabricated accuracy. The deterministic random split is email-disjoint; thread/domain independence and representative class/language coverage still need review before release claims.

## Ask

Open `private_review/final-gate-20261017/ask/ask-development.csv`. It contains existing development questions, actual responses and source mail for local review. Judge `answerable`, `answer_correct`, `source_correct`, `citation_correct`, and `unsupported_factual_answer` as yes/no; fill reviewer/provenance/date. Correctness includes conditions, negation and scope. A valid citation ID alone does not prove an answer correct. An unsupported assertion is still a failure if it carries a warning. An empty result is not proof that the mailbox lacks evidence: inspect relevant mail when judging answerability. Mark clarification as correct only when it is actually necessary.

The empty `ask-holdout.csv` is a question/review template, not an evaluated benchmark. A human must supply independent representative questions across Arabic/English/mixed, travel, existence, status, digest, ambiguity, unsupported, follow-up and clarification-selection cases. Keep them out of development. `history` is a JSON list of at most four prior questions; `selected_email_id` identifies a chosen clarification source when applicable. Before final scoring, freeze the implementation, execute the independent question set once and have a human judge it; do not tune afterward.

    .\env\Scripts\python.exe -m quality.release_review score --kind ask --csv private_review/final-gate-20261017/ask/ask-development.csv

For final task/Ask scoring use `--final --freeze <manifest.json>`. The manifest must bind `review_sha256`, `artifact_sha256`, `selection_complete=true` and `holdout_used_for_selection=false`. The tool writes an exclusive `.consumed.json` receipt before reading the final CSV and refuses reuse. Do not rename/delete the receipt to repeat evaluation. This is an operational safeguard and validates attestations; it cannot establish that a human truly reviewed the data or that sampling is representative. Release approval remains blocked until sample coverage and all acceptance thresholds are independently checked.
